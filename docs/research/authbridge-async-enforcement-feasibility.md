# AuthBridge DG facts and request-time enforcement: feasibility for issue #231

## Source snapshot and scope

This note investigates the **Allow / Block** item in [DG issue #231](https://github.com/rossoctl/lab-data-governance/issues/231). It is a source-based feasibility finding, not an implementation decision. Sources were checked against DG `main` at [`cc7681dd`](https://github.com/rossoctl/lab-data-governance/tree/cc7681dd395b57065731ae4fc7a00a657285c58b) (2026-10-04) and Cortex `main` at [`93a3b74b`](https://github.com/rossoctl/cortex/tree/93a3b74bec32941e68d9f61c98fd485e805141d9) (2026-10-04). Cortex's local checked-out `main` is much older; all Cortex source links below pin `93a3b74b` and use its current `core/` paths.

The first target is a caller-outbound, decoded HTTP request held before forwarding, with **Allow** or **Block** for that same exchange. The configurable deadline defaults to two seconds, and missing decision input causes a separate **service-unavailable rejection**. For ordinary HTTP this renders as HTTP 503; a parsed MCP JSON-RPC request with an ID instead renders an error frame at HTTP 200 ([Cortex rejection renderer](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/listener/httpx/render.go#L33-L65)). Opaque CONNECT remains outside the first guarantee. An earlier proposal had DG return the verdict over a queue. The revised proposal under review has a dedicated DG API return **facts** and Cortex's OPA plugin make the decision; the older DG-verdict and broker sections below remain comparisons, not the current recommendation. These are design inputs, not capabilities already shipped.

## Finding

**Yes, Cortex can receive DG facts and let its OPA plugin enforce before forwarding a visible outbound request.** The lineage plugin's `OnRequest` must wait for matching facts or the deadline before the sequential pipeline reaches OPA; OPA can then return `Continue` or `Reject`, before the forward proxy calls upstream. A plugin-owned receive loop is possible for a streaming transport, though a held request/reply call needs no separate receive loop. The plugin API permits background goroutines in `Init`, provides `Shutdown`, and calls `OnRequest` synchronously ([plugin contract](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/pipeline/plugin.go#L5-L10), [lifecycle](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/pipeline/plugin.go#L120-L149), [pipeline dispatch](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/pipeline/pipeline.go#L84-L130), [forwarding order](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/listener/forwardproxy/server.go#L391-L403), [upstream call](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/listener/forwardproxy/server.go#L528-L536)). DG does not yet have a request-scoped completion barrier across its processors, so that part requires new work.

That is **asynchronous DG work with a synchronous request gate**. Facts arriving after the lineage plugin's `OnRequest` has returned cannot affect the OPA evaluation already made for that exchange. A response-phase rejection could stop delivery of a buffered response, but the upstream action has already run; `OnFinish` executes after response delivery and cannot mutate it ([response hook and finish contract](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/pipeline/plugin.go#L171-L194), [forward-proxy order](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/listener/forwardproxy/server.go#L528-L550)). A stream is therefore possible, but an unheld request cannot be blocked retroactively.

There is an in-tree precedent for background policy state feeding request-time enforcement: the OPA plugin starts the SDK and observes bundle readiness in a background goroutine, then evaluates and rejects in `OnRequest` ([OPA startup](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/opa/plugin.go#L290-L335), [request decision](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/opa/plugin.go#L420-L465)). This proves the lifecycle and gating pattern, though that plugin distributes policy rather than receiving a per-exchange DG verdict.

The earlier queue-only design had one candidate carrying request metadata and available body, followed by one DG verdict; the same lineage plugin would enforce. Its broker reply-routing and payload analysis remains below as a comparison. The revised API/local-OPA direction changes the return payload, policy location, and required report to DG; it also removes broker routing to individual proxy pods if the broker stays behind the API.

## Revised proposal under review: DG facts, Cortex OPA, DG decision report

The proposed control sequence is **request candidate → DG fact snapshot → Cortex OPA verdict and request action → DG decision report**. The current managed `lineage-telemetry` route is not this sequence: it exports OTLP spans asynchronously, and the existing DG HTTP OTLP endpoint returns only an ingestion acknowledgement ([lineage exporter](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L336-L345), [batching](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L451-L465), [DG OTLP HTTP handler](../../data_governance/processors/otlp_receiver/server.py#L303-L337)). DG's current UI API has GET-only resource routes, is deployed as a one-replica UI service, and its NetworkPolicy admits only platform namespaces; its UI HTTPRoute also matches `/`, so control POSTs added to that app would be exposed through the Gateway ([routes](../../data_governance/api/__init__.py#L677-L776), [UI deployment](../../deploy/k8s/40-ui.yaml#L8-L50), [UI route](../../deploy/k8s/60-ui-httproute.yaml#L27-L36), [NetworkPolicy](../../deploy/k8s/50-networkpolicy.yaml#L77-L108)). Proxy workloads need a separate authenticated internal control surface and explicit admission.

For the previously chosen **replies only to pending requests**, one held unary request/reply call to this API is sufficient: the response can contain the fact snapshot once ready, while Cortex's `OnRequest` stays blocked. gRPC reuses HTTP/2 channels and recommends streaming only when it is needed; a separate POST plus WebSocket/SSE channel adds a return-route and reconnection problem across API replicas without providing another required message type ([gRPC performance guidance](https://grpc.io/docs/guides/performance/), [RPC kinds](https://grpc.io/docs/what-is-grpc/core-concepts/), [deadlines](https://grpc.io/docs/guides/deadlines/)). A persistent bidirectional stream remains feasible if the product later needs multiple updates per candidate. This is a transport recommendation to test, not a claim of measured latency.

The proposed DG component cannot simply wait for “all modules.” An outbound request span can produce an Interaction and request leg without its response, and a captured request payload can be classified, but response content/outcome and the callee inbound echo occur only after forwarding ([request derivation](../../data_governance/processors/interactions/sidecar.py#L418-L485), [leg projection](../../data_governance/processors/interactions/sidecar.py#L536-L565), [Cortex response span](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L817-L867)). DG's leg-ready predicate means **leg written and payload classified if present**; it is not a lineage/risk/all-processors barrier ([ADR-0027](../adr/0027-leg-readiness-notification-for-governance-consumers.md#L7-L23), [leg-ready driver](../../data_governance/processors/leg_ready/driver.py#L31-L46)). P-data-lineage independently re-derives a trace as later legs arrive, so its current output is a snapshot over available evidence rather than final completion ([lineage driver](../../data_governance/processors/data_lineage/driver.py#L9-L24)). The unmerged `risk` branch evaluates OPA **inside DG** and does not use `lineage_metadata` in its OPA input; making Cortex OPA authoritative would change that branch's role ([risk pipeline](https://github.com/rossoctl/lab-data-governance/blob/f5d6713a4a451a1b94c48c915bf8ec42adde912b/data_governance/risk/README.md#L72-L107), [risk OPA input](https://github.com/rossoctl/lab-data-governance/blob/f5d6713a4a451a1b94c48c915bf8ec42adde912b/data_governance/risk/engine/utils.py#L414-L452)). A live coordinator therefore needs an explicit, versioned **request-side fact snapshot** and required-fact readiness predicate for the held candidate, with missing and partial facts represented rather than guessed.

The managed attach currently sets `capture_io: false`, so its request span carries no `input.value` for DG's payload classifier. Even with capture enabled, the lineage plugin's default parsed-payload limit is 4096 bytes, and it does not currently declare raw body access; a new candidate API must specify exactly which content it sends, its completeness flag, and its byte cap ([attach configuration](../../deploy/lineage-attach/reconcile-existing-proxy.py#L99-L110), [lineage payload configuration](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/config.go#L69-L92), [lineage capabilities](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L196-L210)).

The existing asynchronous path also cannot promise the two-second default as it stands. The deployed sidecar interaction writer inserts legs without firing `dg_interaction_leg_ready`; that notify exists in the separate streaming interaction writer, and P-classification emits it only when it writes a classification ([sidecar write](../../data_governance/processors/interactions/sidecar.py#L577-L637), [streaming writer tap](../../data_governance/processors/interactions/state.py#L708-L717), [classification tap](../../data_governance/processors/classification/driver.py#L154-L159)). A bodyless or already-classified request can therefore leave the leg-ready consumer waiting for its five-second poll ([poll setting](../../data_governance/processors/leg_ready/driver.py#L68-L77)). The unmerged risk branch also allows five-second OPA calls and retries ([risk configuration](https://github.com/rossoctl/lab-data-governance/blob/f5d6713a4a451a1b94c48c915bf8ec42adde912b/data_governance/risk/config.py#L157-L162), [risk OPA client](https://github.com/rossoctl/lab-data-governance/blob/f5d6713a4a451a1b94c48c915bf8ec42adde912b/data_governance/risk/engine/opa.py#L119-L165)). A live path needs targeted wakeups, candidate-specific progress checks, a bounded computation budget, and a measured deadline failure rate.

In Cortex, the pipeline can run **parsers → lineage/DG fact fetch → OPA**. The lineage hook must put the returned snapshot on `pipeline.Context` only after its own wait completes; background readers cannot mutate that single-goroutine context ([extension contract](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/pipeline/extensions.go#L57-L87)). OPA's `buildInput` currently copies fixed context and typed parser fields, not `Extensions.Custom`, so an explicit schema-checked `input.data_governance` mapping is required ([OPA input builder](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/opa/plugin.go#L520-L562)). OPA already returns request-time Reject on a deny and needs no third enforcer for this first gate ([OPA request evaluation](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/opa/plugin.go#L420-L465)). Its current undefined-policy behavior skips, and `on_error: observe` converts Reject to pass-through; an enforced DG mode must validate both policy readiness and effective pipeline mode ([OPA undefined path](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/opa/plugin.go#L436-L440), [pipeline policy](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/pipeline/pipeline.go#L88-L126)).

For a report of what Cortex **actually did**, the earlier lineage plugin's `OnFinish` runs even when the later OPA plugin rejects; `pctx.Outcome()` then exposes final allow/deny/error and the denying plugin ([finish dispatch](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/pipeline/pipeline.go#L515-L575), [outcome contract](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/pipeline/outcome.go#L50-L76)). That hook runs after response delivery and is best-effort, so a POST from it is not a guaranteed audit receipt and cannot change the request result. On a long-lived stream, `OnFinish` waits for stream end; one completion report could combine response evidence with the applied outcome, but would delay recording the OPA verdict until then ([stream finalization](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/listener/forwardproxy/server.go#L1194-L1220)). It could cover DG timeouts that reject before OPA is dispatched, but the report must distinguish an OPA policy Block from DG unavailability. The current request-rejection path also does not populate `pctx.StatusCode` with the actual wire status; if DG needs it, the listener must supply it ([finish contract](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/pipeline/pipeline.go#L515-L599), [outcome derivation](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/pipeline/outcome.go#L78-L130), [rejection rendering](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/listener/httpx/render.go#L33-L55)).

If only OPA is permitted to POST `/api/decision`, a DG timeout in the earlier lineage plugin must reach OPA as an explicit unavailable input rather than an earlier `Reject`; the pipeline otherwise stops before dispatching OPA, and OPA's `OnFinish` cannot run ([request short-circuit](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/pipeline/pipeline.go#L84-L130), [finish dispatched set](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/pipeline/pipeline.go#L515-L575)). A single earlier reporter can instead cover both normal OPA decisions and earlier transport failures. This is a placement choice; either way, a late or lost report cannot be represented as proof that the proxy applied the DG facts.

Once the dedicated DG API owns the held response, the proxy no longer needs direct broker credentials or a broker reply route. DG already uses Postgres as durable state with cursor drains and `LISTEN`/`NOTIFY` as a wake aid ([ADR-0027](../adr/0027-leg-readiness-notification-for-governance-consumers.md#L24-L36)); an internal broker is optional infrastructure to justify by measured load and fanout. PostgreSQL itself documents `NOTIFY` as a signal rather than a carrier for large records ([PostgreSQL `NOTIFY`](https://www.postgresql.org/docs/current/sql-notify.html)). If the API stores the candidate body once and queues only a candidate ID, the body need not fit a broker record, so the previous RabbitMQ recommendation based on 10 MiB candidate records no longer selects the internal broker. RabbitMQ quorum queues fit acknowledged work dispatch, whereas RabbitMQ Streams, NATS JetStream, and Kafka offer replayable multi-consumer streams under their respective retention models ([RabbitMQ streams](https://www.rabbitmq.com/docs/streams), [JetStream retention](https://docs.nats.io/learn/jetstream/retention-policies), [Kafka consumer groups](https://kafka.apache.org/40/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html#consumergroups)). No p99 winner has been measured; compare deadline latency, replay, duplicates, fanout, and operational cost before introducing a broker.

The body still crosses the proxy-to-DG API. DG's current OTLP gRPC receiver defaults to a 4 MiB receive ceiling, below Cortex's 10 MiB buffered-request ceiling; a new control API needs an explicit body cap or a larger configured receive limit ([DG receiver limit](../../data_governance/processors/otlp_receiver/server.py#L48-L60), [Cortex body ceiling](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/listener/forwardproxy/server.go#L38-L57)). Existing `interaction_payloads.content` is JSONB, so arbitrary raw HTTP bytes also need a bounded parse rule or new binary/blob storage contract ([payload schema](../../data_governance/db/migrations/versions/2026_06_23_0004_interactions_schema.py#L115-L124)).

A first spike for this revised path should use a stub DG fact producer and an OPA rule that reads `input.data_governance`. It should prove that an out-of-order fact reply reaches only its matching held exchange; an OPA Block never reaches upstream; an Allow forwards once; absent, stale, or late facts trigger the configured unavailable rejection; and a final report records **OPA Block**, **DG unavailable**, and **applied outcome** distinctly. A DG-side test should delay each required processor, omit the leg-ready notify, and inject later response evidence to prove that the returned request-time snapshot has a bounded, explicit meaning. Measure the whole candidate → fact snapshot → OPA → forward/reject path against the two-second deadline under load rather than inferring latency from individual components.

## Centralized DG coordination: source findings, not a selected design

The 2026-10-08 design clarification keeps a held request/reply POST and the configurable two-second default. The first DG fact reply must follow request-side interactions/entities, classification, and lineage work; **risk may become mandatory later**, so it is not a first-version release condition. Earlier responses that may affect the held request's lineage are relevant input; the held request's own response cannot arrive until after forwarding. The cutoff for earlier responses that arrive during the held POST and the treatment of partial results remain open decisions.

This follow-up checks DG worktree `feat/279-causal-leg-order` at [`4118dab`](https://github.com/rossoctl/lab-data-governance/tree/4118dab2702ad32e9aa7886acc55725d4ba072be) (2026-10-08); it is ahead of the checked [`origin/main` at `1c538e5`](https://github.com/rossoctl/lab-data-governance/tree/1c538e53cadd3c1fac3f2b56119cf2bb9e7ccb12). The new causal-order and dirty-trace machinery below is therefore **feature-branch code**, not an assumed deployed capability ([ADR-0034](../adr/0034-trace-local-causal-leg-order.md#L30-L50), [dirty-trace migration](../../data_governance/db/migrations/versions/2026_10_06_0021_causal_leg_order.py#L38-L50)). There is still no held `/api/message` coordinator in this source; the present OTLP receiver returns an ingestion acknowledgement and the deployed processors have no inbound Service ([receiver](../../data_governance/processors/otlp_receiver/server.py#L303-L337), [interactions deployment](../../deploy/k8s/70-interactions.yaml#L1-L18), [classification deployment](../../deploy/k8s/80-classification.yaml#L1-L16)).

**The existing request-side dependency graph is narrower than “all modules, for every span.”** A new API must first persist an outbound candidate in the existing sidecar request-span shape, or provide an equivalent adapter. The sidecar algorithm creates no exchange from a span without an exchange ID, anchors an outbound *request* span, and derives its caller/callee entities, Interaction, request leg and optional content-addressed payload while the matching response span is absent; the response leg appears only after its span arrives ([sidecar planning](../../data_governance/processors/interactions/sidecar.py#L370-L485), [leg projection](../../data_governance/processors/interactions/sidecar.py#L536-L565), [write order](../../data_governance/processors/interactions/sidecar.py#L569-L637)). From the produced payload, P-classification computes a write-once verdict keyed by content hash; if no payload was extracted, classification is **not applicable in the current pipeline**, rather than pending. That says nothing about whether raw HTTP body bytes existed or were safe: payload extraction currently depends on the protocol parser and `input.value` ([classification input/write](../../data_governance/processors/classification/driver.py#L70-L111), [leg-readiness predicate](../../data_governance/processors/leg_ready/driver.py#L125-L137), [sidecar payload extraction](../../data_governance/processors/interactions/sidecar.py#L219-L231), [wire contract](../sidecar-wire-contract.md#L33-L36)). P-data-lineage consumes the request leg independently of classification and re-derives the whole trace from the legs and entities then visible ([lineage driver](../../data_governance/processors/data_lineage/driver.py#L9-L31), [trace read](../../data_governance/processors/data_lineage/driver.py#L119-L174)). Thus classification and data lineage can run in parallel after P-interactions commits; an eventual risk stage would need its own explicit prerequisites. Risk is absent from this branch's code; the unmerged risk branch instead starts from leg readiness and calls OPA inside DG, so it is not already a Cortex-OPA fact producer ([risk branch pipeline](https://github.com/rossoctl/lab-data-governance/blob/f5d6713a4a451a1b94c48c915bf8ec42adde912b/data_governance/risk/README.md#L72-L104)).

**There is no request-specific completion barrier today.** Each worker independently drains a source table in `seq` order, commits its derived rows with a *global* `processor_state` cursor, and treats payload-less PostgreSQL notifications only as wake hints ([shared driver](../../data_governance/processors/_driver.py#L11-L26), [cursor write](../../data_governance/processors/_driver.py#L84-L125)). `dg_interaction_leg_ready` proves only “leg written and payload classified, if present”; it does not wait for data lineage or risk ([ADR-0027](../adr/0027-leg-readiness-notification-for-governance-consumers.md#L15-L26), [leg-ready consumer](../../data_governance/processors/leg_ready/driver.py#L31-L46)). Nor can a coordinator equate `lineage_trace_status.status = complete` with “lineage was computed for this candidate”: the status row has no source revision, and a bodyless leg legitimately produces a **computed `partial`** lineage result; the feature branch also documents a missing-producer case in which `complete` can coexist with no metadata row for that leg ([status schema](../../data_governance/db/migrations/versions/2026_07_28_0014_lineage_trace_status.py#L93-L110), [traversal cutoff](../../data_governance/processors/data_lineage/traversal.py#L244-L264), [missing-producer caveat](../../data_governance/processors/data_lineage/driver.py#L443-L492)). The feature branch's generation-keyed `data_lineage_dirty_traces` queue repairs later parent/leg corrections, but it is a **lineage invalidation queue**, not a cross-processor candidate completion record ([migration](../../data_governance/db/migrations/versions/2026_10_06_0021_causal_leg_order.py#L53-L83), [redrive](../../data_governance/processors/data_lineage/driver.py#L647-L681)).

A coordinator could own the **candidate lifecycle and fact snapshot** without owning every calculation. One concrete contract to test is: persist a stable `(trace_id, exchange_id)` and input revision; wait for P-interactions to commit the *matching request leg*, for classification of its payload hash **or an explicit no-payload result**, and for data lineage (and any required risk stage) to commit outputs for the same relevant trace revision; then assemble the OPA facts in one consistent read, marking lineage coverage and unavailable fields explicitly. The exchange ID is already the request span's own span ID and the response span echoes it ([wire contract](../sidecar-wire-contract.md#L38-L54)); P-classification keys its output by hash ([classification schema](../../data_governance/db/migrations/versions/2026_07_14_0008_payload_classifications.py#L77-L89)); and the current lineage correction path demonstrates why a trace revision matters when parentage, endpoint, payload or occurrence time changes without a new leg `seq` ([lineage driver](../../data_governance/processors/data_lineage/driver.py#L26-L48), [ADR-0034](../adr/0034-trace-local-causal-leg-order.md#L30-L39)). These candidate/stage revision markers **do not exist yet**; a global cursor or notification alone cannot substitute for them. A request-time snapshot may include already-ingested responses to *other, causally earlier* exchanges; a response to the **held exchange** cannot arrive before it is forwarded. Later response evidence should advance DG's observation revision and improve subsequent snapshots, without silently rewriting facts already returned for an OPA decision ([sidecar request/response pairing](../../data_governance/processors/interactions/sidecar.py#L458-L484), [causal-order rule](../adr/0034-trace-local-causal-leg-order.md#L7-L20)).

**A reliable cutoff for earlier responses is not present in the current wire contract.** Cortex creates the response span only in `OnFinish`, after the listener has written the response, and exports it through an asynchronous batcher; a later held candidate can reach DG before the earlier response span ([finish timing](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/pipeline/pipeline.go#L515-L522), [lineage response span](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L817-L867), [batch exporter](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L459-L465)). Its `lineage.exchange.id` pairs one request and response, its `tracestate` stamp carries ancestry, and its `RequestID()` pairs session events, but none is a producer observation sequence or a receipt watermark ([exchange ID](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L618-L625), [parent stamp](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L714-L760), [request ID contract](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/pipeline/requestid.go#L13-L37)). DG's `spans.seq` is allocated when a span is stored, so it cannot reveal a producer observation that has not arrived; its span-finalization ADR also explicitly defers high-water-mark gap handling ([span insert](../../data_governance/processors/otlp_receiver/write_span.py#L160-L187), [ADR-0004](../adr/0004-span-finalization-model.md#L84-L96)).

Streaming widens that gap. Cortex forwards and flushes parsed SSE frames before the final `OnResponseFrame(last=true)` and `OnFinish`; raw SSE passthrough flushes chunks without a per-frame plugin hook ([parsed SSE](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/listener/forwardproxy/server.go#L1194-L1276), [raw passthrough](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/listener/forwardproxy/server.go#L1300-L1355)). An agent can act on an earlier frame while that stream remains open. If the required fact snapshot must cover **all earlier caller-visible response data**, Cortex needs a new producer instance/epoch ID and monotonic observation sequence, the candidate must carry a cutoff, and DG must verify a contiguous received prefix and matching stage completion. The relevant observation must be registered before delivery; incrementing a counter in `OnFinish` is too late. Streaming additionally needs per-frame or per-chunk observations at a pre-delivery point, or an explicit unknown/unsupported lineage state for live streams. One producer's cutoff cannot prove that DG received another sidecar's observations, even within one trace. Current data lineage is deliberately intra-trace, with cross-trace flow deferred ([lineage scope](../../data_governance/processors/data_lineage/driver.py#L61-L65), [retrieval scope](../../data_governance/retrieval/lineage_graph.py#L85-L89)). Whether this stronger caller-visible guarantee is required is still a product decision; a snapshot of evidence already committed in DG has weaker, but well-defined, coverage.

Two implementation shapes remain plausible. An **outer coordinator** can write the candidate, wait on explicit stage completion records, and leave the existing workers as sole writers of their tables; targeted notifications merely wake a candidate-specific DB check. If measured latency requires a priority path, an **explicit stage runner** can call or RPC the same derivation/classification/lineage implementations and commit stage outputs under trace ownership. It must not simply invoke `sidecar.derive_trace` in an API replica while the existing P-interactions worker also reconciles that trace: the sidecar writer deletes and re-inserts the trace's `interaction_spans`, and explicitly treats an insert conflict as evidence of an unsupported concurrent writer ([sidecar writer](../../data_governance/processors/interactions/sidecar.py#L662-L695), [single-writer deployment](../../deploy/k8s/70-interactions.yaml#L13-L26)). In-process classification in the API is likewise not a cheap import of the current deployment: its loaded NER model lives in a separate image with torch and roughly 500 MB of weights ([classification deployment](../../deploy/k8s/80-classification.yaml#L12-L20), [model startup](../../data_governance/processors/classification/__main__.py#L145-L150)). An internal broker may dispatch stage work, but by itself supplies neither a consistent revision nor the completion predicate.

The existing workers cannot promise the default two-second held POST. They are single-replica, cursor-ordered drainers; P-interactions reconciles a whole trace per arriving span, data lineage re-derives a whole trace per leg, and classification runs model inference per payload ([interactions driver](../../data_governance/processors/interactions/sidecar_driver.py#L9-L20), [lineage driver](../../data_governance/processors/data_lineage/driver.py#L9-L24), [classification driver](../../data_governance/processors/classification/driver.py#L83-L111)). Their lost-notification fallback polls every five seconds, and leg readiness can be held behind another unclassified leg's lower `seq` ([shared driver](../../data_governance/processors/_driver.py#L217-L256), [leg-ready driver](../../data_governance/processors/leg_ready/driver.py#L63-L77), [ADR-0027](../adr/0027-leg-readiness-notification-for-governance-consumers.md#L58-L68)). The branch has no end-to-end latency measurement for candidate ingest → required stage commits → fact assembly. The open design inputs are **what counts as a completed classification and lineage calculation when evidence is absent or partial**, which prior-response evidence the snapshot must include, and whether live streams need caller-visible coverage. Those choices determine the readiness predicate, the source revision boundary, and whether a priority path is necessary; the two-second deadline remains the final limit rather than a reason to return unstated partial facts.

## Why the current telemetry route cannot be the control route

DG's attach configuration points `lineage-telemetry` at the platform OTel collector and sets `capture_io: false` ([attach configuration](../../deploy/lineage-attach/reconcile-existing-proxy.py#L99-L110), [collector endpoint](../../deploy/dg.sh#L830-L841)). Cortex ends the request span **inside `OnRequest`**, before the proxy forwards upstream, but exports it with an asynchronous batch processor ([span emission](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L610-L643), [batch processor](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L451-L465)). The collector adds another `batch` stage before DG ([collector pipeline](../../deploy/patch-rossoctl-collector.sh#L155-L168)). Thus span creation precedes forwarding, but DG receipt does **not** have a guaranteed order relative to forwarding.

The DG copy of the wire contract says the request span is emitted once the request was “seen and forwarded” ([wire contract](../sidecar-wire-contract.md#L35-L43)). The current Cortex code emits and ends it before the forward proxy's upstream `client.Do`, so that wording is too strong for enforcement or delivered-data claims. The request span proves an observed attempt; the later response/outcome span records the result ([response span](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L817-L868)). A joint wire-contract correction would need to be made in both repositories because the contract says its two copies stay byte-identical ([contract ownership](../sidecar-wire-contract.md#L1-L12)).

The current DG gRPC receiver implements the unary OTLP `TraceService.Export` operation and returns success or OTLP `partial_success` for ingestion, with no decision field ([DG receiver](../../data_governance/processors/otlp_receiver/server.py#L164-L202); [official trace service proto](https://github.com/open-telemetry/opentelemetry-proto/blob/main/opentelemetry/proto/collector/trace/v1/trace_service.proto)). The OTel collector is an intermediary, so an invented response field at DG would not be a reliable reply to the originating plugin. A separate control request and reply path is needed for a per-exchange verdict, whether direct or brokered. DG's accepted leg-readiness ADR anticipates a future PDP that decides whether a leg may proceed, yet readiness requires a persisted leg and, when there is a payload, its completed classification ([ADR-0027](../adr/0027-leg-readiness-notification-for-governance-consumers.md#L1-L23), [glossary](../../CONTEXT.md#L513-L529)). That event can inform later decisions; it cannot by itself hold the request that produced the telemetry.

## Earlier comparator: direct DG verdict RPC

The following direct RPC shape is a proposed baseline for comparison, **not** an existing protocol:

1. In the outbound request hook, snapshot the facts DG needs for one candidate and assign a globally unique candidate ID. If linking to lineage spans, carry trace ID plus span/exchange ID; AuthBridge's existing `RequestID()` is explicitly only unique within one process and should not be the sole cross-pod key ([request ID contract](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/pipeline/requestid.go#L10-L18)).
2. Send the candidate directly to a new DG decision endpoint before upstream forwarding. Receive only a reply for that pending candidate, with its ID, `Allow` or `Block`, and enough policy/decision identity to audit it. A unary request/reply RPC is sufficient for this exact requirement; a persistent bidirectional gRPC stream is technically possible if multiplexing or DG-side asynchronous work warrants it ([gRPC Go streaming contract](https://grpc.io/docs/languages/go/basics/#bidirectional-streaming-rpc)). Neither operation exists in DG today ([current OTLP service](../../data_governance/processors/otlp_receiver/server.py#L164-L202)).
3. Under a stream transport, let a plugin-owned receive loop route the reply to the waiting request hook; with unary RPC, the request goroutine receives its own reply. The hook waits on verdict, caller cancellation, and the configured deadline. A matching `Block` returns `Reject`; `Allow` returns `Continue`; lost connection, invalid/late verdict, or deadline takes the defined service-unavailable path. Caller cancellation terminates the pending candidate without forwarding. A late reply must never change a request already forwarded or rejected. A receiver goroutine should not retain or mutate `pipeline.Context`; Cortex explicitly treats contexts as single-goroutine state and warns against late attribution after a hook returns ([context contract](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/pipeline/requestid.go#L49-L53), [dispatch warning](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/pipeline/pipeline.go#L96-L102)).
4. Bound in-flight candidates, clean them up on cancellation/reconnect/shutdown, and make the control connection's readiness independent from the telemetry exporter. `on_error: observe` converts a returned `Reject` into pass-through, so enforcement deployment must use `enforce` (the default) and verify its effective configuration ([policy modes](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/pipeline/policy.go#L3-L40), [dispatch](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/pipeline/pipeline.go#L116-L126)).

This requires an authenticated and admitted proxy-to-DG route. The current DG receiver NetworkPolicy admits its OTLP ports only from three platform namespaces, while `dg.sh instrument` selects agent/tool workloads in a caller-specified namespace ([NetworkPolicy](../../deploy/k8s/50-networkpolicy.yaml#L48-L65), [instrument scope](../../deploy/dg.sh#L830-L836)). It does not admit an arbitrary instrumented workload namespace to a decision service. The proxy's own UID is exempt from AuthBridge's transparent iptables redirect, so a direct proxy-originated connection need not loop back through its own pipeline ([proxy-init rules](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/deploy/proxy-init/README.md#L45-L70)). Namespace admission alone is not a proxy identity check; DG would need to authenticate the caller, and Cortex would need to authenticate DG, before trusting an Allow verdict. The transport, credentials, and service placement remain design decisions.

## Earlier option: replacing both telemetry and verdict paths with a queue

A full queue design is technically possible. At `OnRequest`, AuthBridge would publish a typed decision candidate and hold that request while an always-running DG consumer evaluates it. DG would publish an `Allow` or `Block` reply; a plugin-owned consumer would route that reply to the waiting hook. In parallel, the lineage plugin would publish spans for a DG telemetry consumer. One broker can serve both paths, but telemetry may batch, retry, and replay while candidates and replies have a hard request deadline. They need separate topics and consumer groups, or equivalent capacity isolation, so a telemetry backlog cannot consume the live decision budget. The plugin still has to enforce the deadline locally and return the specified service-unavailable rejection when no valid reply arrives. The same `OnRequest` forwarding boundary described above remains the enforcement point.

This is a real migration of the present telemetry route: Cortex needs a broker span exporter, DG needs a broker consumer/adapter, and the collector pipeline and deployment wiring need to change ([current Cortex batch exporter](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L451-L465), [collector pipeline](../../deploy/patch-rossoctl-collector.sh#L155-L168), [DG OTLP receiver](../../data_governance/processors/otlp_receiver/server.py#L164-L202)). The span payload can still use OTLP protobuf: the [official OTel Collector Kafka exporter](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/787258321e670c7250e8d8c7092d7d36902c4006/exporter/kafkaexporter/README.md) supports `otlp_proto`. Replacing only the collector-to-DG leg with that exporter would leave plugin-to-collector OTLP in place, so it would not be the proposed full replacement. A queue *after* OTLP remains a useful independent telemetry buffer, but does not supply a verdict to the held request.

For the control leg, candidate IDs must be unique across proxies, replies must reach the originating live proxy instance, and both sides must handle expiry, cancellation, duplicate delivery, late replies, reconnects, and a decision audit record. A broker does not itself guarantee the proposed two-second deadline. The Collector's [Kafka exporter](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/787258321e670c7250e8d8c7092d7d36902c4006/exporter/kafkaexporter/README.md) documents a synchronous producer, a sending queue, a five-second produce timeout, and retries; the [Kafka receiver](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/787258321e670c7250e8d8c7092d7d36902c4006/receiver/kafkareceiver/README.md) documents fetch waits, offset commits, and redelivery after rebalances. Those are telemetry-friendly delivery tools, not proof that a candidate and reply can finish before Cortex's deadline. The control consumers should stay warm for this deadline, and the spike must measure end-to-end latency and unavailable rejections under lag and rebalance.

Kafka reply routing needs a separate design for many short-lived sidecars. A record key chooses a partition, while a subscribed consumer group assigns that partition to one of its members, which need not be the proxy holding the candidate ([Kafka producer record](https://kafka.apache.org/40/javadoc/org/apache/kafka/clients/producer/ProducerRecord.html), [consumer groups](https://kafka.apache.org/40/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html#consumergroups)). Possible return routes have distinct costs: a topic per proxy needs dynamic topics and access rules; a unique consumer group per proxy reads and filters every verdict; a partition per proxy needs an owner allocator and manual assignment; a stable router adds a component and another delivery hop ([Kafka manual assignment](https://kafka.apache.org/40/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html#manualassignment)). The platform example has one EventBridge replica consuming responses and storing them centrally before serving its HTTP callers, not replies routed to dynamic AuthBridge pods ([deployment](https://github.com/rossoctl/examples/blob/d9677ddd1611afd05fe51fcdc0dee0cd27809e62/eventing/k8s/base/eventbridge-deployment.yaml#L1-L20), [consumer setup](https://github.com/rossoctl/examples/blob/d9677ddd1611afd05fe51fcdc0dee0cd27809e62/eventing/eventbridge/__main__.py#L90-L97), [response consumer](https://github.com/rossoctl/examples/blob/d9677ddd1611afd05fe51fcdc0dee0cd27809e62/eventing/eventbridge/kafka_in.py#L31-L39)). A queue spike must prove reply readiness and routing through pod churn, then measure its topics, consumers, traffic, and latency.

Core NATS has a native reply-subject pattern that can address the requesting connection, but its at-most-once delivery does not itself provide retained evidence ([NATS request/reply](https://docs.nats.io/learn/core-nats/request-reply), [Core NATS delivery](https://docs.nats.io/learn/core-nats/)). JetStream can retain a shared stream and use filtered consumers for reply subjects, but consumer lifecycle, expiry, access rules, and the two-second deadline still require a spike ([JetStream filtering](https://docs.nats.io/learn/jetstream/filtering)). This is a routing comparison, not a broker recommendation.

The broker can retain correlated candidate, DG decision, and Cortex outcome events for replay and audit, but each record proves a different fact. A broker acknowledgement proves publication according to its configuration; a verified, retained DG `Block` records a decision, **not** that Cortex applied it. The platform example's Strimzi topics retain events for 24 hours, which by itself is not a long-term audit record ([eventing retention](https://github.com/rossoctl/rossoctl/blob/6c59d27bf1e23ff434ec737c0f921b3d7f571205/docs/eventing/index.md#L39-L43)). To establish application, Cortex would need an acknowledged report of the effective action with the same candidate ID from a point after pipeline policy handling; `on_error: observe` can turn a plugin `Reject` into pass-through ([policy modes](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/pipeline/policy.go#L3-L40), [dispatch](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/pipeline/pipeline.go#L116-L126)). A guarantee that this report survives a broker outage or proxy crash requires a local durable outbox or explicit loss semantics. DG database commit and broker reply publication are separate writes, so their order and recovery behavior must be specified. These are design requirements to validate, not features of the current code.

The selected audit order is for DG to **commit its verdict to its database before publishing the reply**. The row should be keyed by candidate ID so redelivered candidates reuse the same decision and decision ID; if publication fails after commit, DG must retry that stored reply or Cortex reaches its deadline and rejects as unavailable. A reply published before the candidate is acknowledged may be duplicated on redelivery, so Cortex must ignore repeats and late replies. This order records DG's decision before Cortex can act on it, but still does not record Cortex's effective action; the queue consumer, database, and publisher transaction boundaries need a concrete recovery design.

There is relevant platform precedent, but its availability for DG is unproven. The platform docs mark an **alpha example** in which EventBridge publishes requests to Kafka, EventRunner consumes them, and replies return through Kafka; its KEDA runner can scale to zero and its request age defaults to an hour ([eventing path and status](https://github.com/rossoctl/rossoctl/blob/6c59d27bf1e23ff434ec737c0f921b3d7f571205/docs/eventing/index.md#L8-L52)). That demonstrates a brokered exchange, not an installed broker in the target DG cluster or a two-second decision service. The example's identity controls are off by default and its broker connection is plaintext ([eventing warning](https://github.com/rossoctl/rossoctl/blob/6c59d27bf1e23ff434ec737c0f921b3d7f571205/docs/eventing/index.md#L14-L23), [identity limits](https://github.com/rossoctl/rossoctl/blob/6c59d27bf1e23ff434ec737c0f921b3d7f571205/docs/eventing/identity.md#L210-L215)); enforcement would require authenticated publishing and verified replies, plus new topics, access rules, and always-on consumers. If a suitable hardened broker already operates in the target cluster, reusing it could reduce infrastructure cost; otherwise broker deployment and operation are additional work.

At 2026-10-05 07:43 UTC, read-only `kubectl` inventory of the configured `kind-rossoctl` context showed a running DG namespace but no broker workload by name/image, no broker Service by name, no Strimzi CRD, and no broker-related DG deployment environment variable or ConfigMap name. The inspection used `kubectl get deployments,statefulsets,pods,services -A`, `kubectl get crd -o name`, and DG deployment/ConfigMap metadata; it read no Secret or ConfigMap values. This is a time-scoped finding for the local kind cluster, not evidence about another target cluster or an external managed broker.

If telemetry remains, a queue can carry telemetry and decisions through one broker with replayable evidence and independently scaled DG consumers. Under the proposed strict two-record path, a direct RPC can carry the same candidate and verdict, while DG persists its decision before replying; it need not retain OTLP either. A queue then adds broker retention and decoupling but also an extra routing problem and, in the inspected cluster, new infrastructure. Queue durability cannot rescue a verdict that arrives after the request deadline. Neither transport should be selected without measuring the live control path and confirming the target broker and security posture.

## Message and byte budget for a queue design

Payload bytes, broker records, network hops, and latency are separate budgets. The core gate needs **one candidate** from Cortex to DG and **one correlated verdict** from DG to Cortex per held exchange. If applied-action evidence is required, add **one acknowledged outcome** from Cortex after the effective pipeline action. A two-record broker path still sends each payload producer→broker→consumer, plus acknowledgements and any replication; a direct RPC uses one Cortex→DG hop and its reply. Kafka's producer `batch.size` and `linger.ms` can group individual records into a produce request, and `compression.type` compresses record batches; these change requests and bytes on the wire, not the count of logical candidate/verdict records ([Apache Kafka producer configuration](https://kafka.apache.org/40/configuration/producer-configs/)). Waiting for more records on either control producer spends the two-second request budget. Packing several candidates into one application-level array, JSON or binary, *would* reduce broker record count, but requires accumulation time and per-candidate IDs, deadlines, and failure handling; it is unsuitable as the default control path. Telemetry can batch independently. The chosen Go/Python clients and representative payloads must be measured before claiming a byte or latency advantage from batching or compression.

The minimum combined-evidence variant can use three logical records: candidate **plus request evidence** (Cortex→DG), verdict (DG→Cortex), and effective action **plus response evidence** (Cortex→DG). That is two outbound records and one inbound record per exchange, including the applied-outcome audit report. It is feasible in principle, but the first candidate becomes larger and time critical. Cortex currently creates an OTLP/gRPC exporter and batches spans in the OTel SDK ([exporter setup](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L336-L345), [SDK batcher](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L451-L465)); combining a candidate with its request span would require refactoring that export path so the candidate publishes immediately. The simpler variant keeps candidate and verdict records small and batches span telemetry separately; its total telemetry record count depends on batch size. DG already parses OTLP protobuf `ExportTraceServiceRequest` and iterates its spans ([protobuf decode](../../data_governance/processors/otlp_receiver/server.py#L277-L289), [span iteration](../../data_governance/processors/otlp_receiver/translate.py#L52-L75)), while the [Collector Kafka exporter](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/787258321e670c7250e8d8c7092d7d36902c4006/exporter/kafkaexporter/README.md) supports `otlp_proto` as a queue payload. Either variant still needs a new DG broker adapter and a way to report the *effective* action. A three-record layout alone does not guarantee that this post-action report survives a proxy crash; strict applied-audit semantics remain open.

For a first control wire format, use a **versioned binary protobuf** envelope with candidate ID, reply route, expiry, and only the facts DG needs to decide; the reply needs candidate ID, an `Allow`/`Block` enum, and decision ID. Binary protobuf sends numbered wire tags and values, **not the schema's field names**, and `repeated` fields encode arrays; a `bytes` body also avoids JSON base64 expansion ([protobuf wire format](https://protobuf.dev/programming-guides/encoding/), [proto3 repeated fields](https://protobuf.dev/programming-guides/proto3/#specifying-field-rules)). OTLP is already protobuf, but its extensible attributes use `KeyValue` entries with a **string key**, so names such as `lineage.self.id` are transmitted for each attribute; fixed fields in a purpose-built candidate avoid that overhead ([OTLP `KeyValue` schema](https://github.com/open-telemetry/opentelemetry-proto/blob/main/opentelemetry/proto/common/v1/common.proto)). Keep trace and span IDs as bytes, as OTLP does before DG stores them as hex ([DG translation](../../data_governance/processors/otlp_receiver/translate.py#L12-L15)). Protobuf's [schema update rules](https://protobuf.dev/programming-guides/proto3/#updating) provide a documented way to add fields. A positional JSON array for one candidate might save repeated key text, but it needs its own versioned index contract and explicit rules for missing values; it does not reduce record count. Compare encoded bytes, broker records per exchange, and publish-to-verdict latency before claiming a size or speed win.

## Earlier option: only a candidate and DG verdict

A strict **two-record** version publishes one request candidate from Cortex and one verdict from DG, with no OTLP spans and no later Cortex outcome or response record. It can still gate a held outbound request: the DG consumer decides, the plugin's background consumer finds the waiting `OnRequest`, and that hook returns before upstream forwarding. It is **not** a drop-in replacement for the current DG input. `P-interactions` asynchronously consumes stored spans; an outbound request span alone can create caller/callee entities, an Interaction, and a request leg without waiting for a response, leaving the Interaction in flight until a response span arrives ([sidecar driver](../../data_governance/processors/interactions/sidecar_driver.py#L41-L68), [request anchor and optional response](../../data_governance/processors/interactions/sidecar.py#L418-L485), [write path](../../data_governance/processors/interactions/sidecar.py#L577-L637), [prefix-arrival integration test](../../tests/processors/interactions/test_sidecar_write_integration.py#L149-L174)). If both spans land before a drain, the first persisted row may already be complete. The sidecar derivation also uses callee-side inbound echoes to refine identity and the interaction tree ([P-interactions glossary](../../CONTEXT.md#L470-L492), [echo derivation](../../data_governance/processors/interactions/sidecar.py#L444-L475)). Queue candidates need a new ingestion and derivation adapter; without callee-side facts, even adding an outcome record would not automatically recreate every identity and tree edge.

Trace ancestry must be carried deliberately if those spans disappear. Today each lineage element, inbound and outbound, creates a request span whose **own span ID** is its exchange ID, selects its parent from `tracestate`'s `lineage-parent` stamp before falling back to the wire `traceparent`, and re-stamps the forwarded request with its new ID. A valid `traceparent` is normally left untouched; when none exists, the plugin mints one so the stamp can propagate ([Cortex parent selection and ID](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L589-L625), [Cortex propagation](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L646-L760), [wire contract](../sidecar-wire-contract.md#L79-L143)). A replacement candidate needs the trace ID, its own stable lineage-element/exchange ID, the **selected parent ID** (not merely the raw `traceparent` parent), parent source, direction, workload namespace/self ID, and peer facts if DG is to rebuild the existing graph; a separate globally unique candidate ID can route the live verdict. The current derivation follows stored parent IDs to find anchor ancestry and uses the callee's inbound echo to replace a provisional peer host with canonical workload identity ([anchor walk and echo](../../data_governance/processors/interactions/sidecar.py#L418-L475), [callee rule](../../data_governance/processors/interactions/sidecar.py#L252-L269)). If only outbound candidates are published, the callee's inbound element remains invisible: a later outbound candidate from that callee may point to an absent inbound ID, and DG cannot reconstruct that causal link or the callee-side identity from the two records alone. Preserving those facts requires inbound observations or a newly specified, trustworthy correlation scheme in the candidates.

| Record or missing observation | What DG can establish |
|---|---|
| Cortex request candidate | An **attempt** with the request facts and content it actually carries. It is created before forwarding, so it is not proof of upstream delivery. |
| DG `Allow` / `Block` verdict | DG's decision for that candidate. It does not prove the proxy received or applied the decision; a late or lost reply can produce a local service-unavailable rejection, and Cortex's `on_error: observe` mode can turn a plugin `Reject` into pass-through ([pipeline policy](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/pipeline/policy.go#L3-L40), [dispatch](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/pipeline/pipeline.go#L116-L126)). |
| No Cortex completion or response observation | No evidence of the effective action, upstream response, completion time, duration, HTTP status, error, or response content. In the current derivation, an absent response means an in-flight interaction with no response leg ([sidecar row and leg projection](../../data_governance/processors/interactions/sidecar.py#L194-L249), [leg projection](../../data_governance/processors/interactions/sidecar.py#L536-L565), [interaction-leg glossary](../../CONTEXT.md#L243-L276)). |

If a new adapter persists the candidate's request payload, DG could still classify that request. Its classifier currently drains `interaction_payloads` asynchronously; the existing leg-ready event waits for that classification, so using it for the same held request would also have to meet the verdict deadline ([classification drain](../../data_governance/processors/classification/driver.py#L168-L190), [leg-readiness ADR](../adr/0027-leg-readiness-notification-for-governance-consumers.md#L7-L20)). The two-record wire never provides tool results, LLM completions, or agent responses for classification ([classification content kinds](../../data_governance/processors/classification/projection.py#L111-L125)). The current attach configuration has `capture_io: false`, so that deployed route already omits both request and response bodies; it still carries response outcome and status today ([attach configuration](../../deploy/lineage-attach/reconcile-existing-proxy.py#L99-L110), [wire attributes](../sidecar-wire-contract.md#L189-L193)).

"Body if available" needs an explicit byte contract. The deployed attach chain includes MCP, A2A, and inference parsers, each declaring request-body access, so the forward proxy buffers a non-skipped HTTP request body before calling the lineage plugin ([attach chain](../../deploy/lineage-attach/reconcile-existing-proxy.py#L99-L110), [MCP parser](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/mcpparser/plugin.go#L89-L94), [A2A parser](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/a2aparser/plugin.go#L28-L33), [inference parser](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/inferenceparser/plugin.go#L40-L45), [forward proxy buffering](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/listener/forwardproxy/server.go#L356-L368)). That listener has a 10 MiB body ceiling and rejects a larger buffered request before the pipeline runs ([body cap and rationale](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/listener/forwardproxy/server.go#L38-L57)). Sending the whole buffer in each candidate could therefore transmit far more body bytes than today's `capture_io: false` OTLP route, despite fewer broker records. Candidate body completeness, size cap, and the action for an oversized record need a contract before a network-load claim can be made.

A full 10 MiB body plus its envelope also exceeds common default single-message limits. Kafka 4.0 documents a 1,048,576-byte Java producer `max.request.size` for the uncompressed record batch and a 1,048,588-byte broker/topic maximum after compression ([producer setting](https://kafka.apache.org/40/configuration/producer-configs/#producerconfigs_max.request.size), [broker setting](https://kafka.apache.org/40/configuration/broker-configs/#brokerconfigs_message.max.bytes), [topic override](https://kafka.apache.org/40/configuration/topic-level-configs/#topicconfigs_max.message.bytes)); a future Cortex Go producer would need its corresponding limit checked. NATS 2.14 defaults `max_payload` to 1 MB, permits a larger configured value, and advises against more than 8 MB; JetStream's stream-level `max_msg_size = -1` does not override the server limit ([NATS server setting](https://docs.nats.io/reference/2.14/config/max_payload), [JetStream stream setting](https://docs.nats.io/reference/2.14/jetstream/api/stream/create)). A one-record candidate containing the largest accepted body therefore needs a smaller body contract, larger broker/client limits, or body chunking; chunking would break the proposed one-record budget. Actual broker and client configuration must be checked in the spike.

The direct-RPC comparator also needs an explicit candidate limit: gRPC Go v1.84.0 and the gRPC C core used by DG default server receives to 4 MiB, and both expose receive-size configuration ([Go default and option](https://github.com/grpc/grpc-go/blob/v1.84.0/server.go#L60-L62), [Go option](https://github.com/grpc/grpc-go/blob/v1.84.0/server.go#L448-L453), [gRPC core default](https://github.com/grpc/grpc/blob/v1.80.0/include/grpc/impl/channel_arg_names.h#L40-L49)). DG's existing OTLP server explicitly configures a 4 MiB default ([receiver setting](../../data_governance/processors/otlp_receiver/server.py#L48-L60), [server setup](../../data_governance/processors/otlp_receiver/server.py#L211-L226)). A new DG decision RPC could raise its receive ceiling or use a bounded candidate; like a queue, its defaults cannot accept the largest Cortex body in one message.

Response content is also the callee-to-caller half of DG's data-lineage walk. Removing it loses how tool or LLM data entered the caller ([lineage routing](../../data_governance/processors/data_lineage/traversal.py#L28-L36), [glossary](../../CONTEXT.md#L719-L724)). A fabricated response leg with no payload is not a safe placeholder: current traversal stops the whole trace at its first null payload and reports `partial`; omitting the leg could instead report `complete` over a deliberately request-only graph ([traversal cutoff](../../data_governance/processors/data_lineage/traversal.py#L237-L246), [implementation](../../data_governance/processors/data_lineage/traversal.py#L289-L309)). A request-only product therefore needs its own coverage meaning and must not claim complete two-way lineage.

If issue #231 needs auditable *applied* enforcement and the existing response-side DG capabilities, retain or add a Cortex completion observation carrying the effective action and available response facts/content, correlated with the candidate. An action-only receipt would establish a different fact from response content and would not restore response classification or lineage. If the intent is solely live request gating plus a log of DG decisions, two records are enough for that narrower product, subject to the deadline and reply-routing spike; the records must be named as an attempt and a decision, not an applied block or a completed interaction.

## Earlier broker choice for the two-record gate

No reusable production queue broker was found in the inspected standard platform deployment or local DG cluster. The documented platform Kafka exchange is an alpha example in another repository, and Cortex's current pinned `main` does not contain the older local checkout's opt-in AIAC NATS manifest. If there is no external managed broker for the target environment, this design needs a DG-owned deployment. The following compares broker primitives for **one durable candidate and one reply to the waiting proxy**, with DG committing its decision before reply; no p99 latency or operating-cost ranking has been measured.

| Broker | Candidate and return route | Relevant default payload limit |
|---|---|---|
| **RabbitMQ 4.1** | A quorum queue provides durable candidate delivery with publisher confirms and manual consumer acknowledgements. Direct Reply-To sends the verdict to the requesting connection without a reply queue per sidecar; this reply is volatile and can be discarded on disconnect, which takes Cortex's service-unavailable path ([quorum queues](https://www.rabbitmq.com/docs/4.1/quorum-queues), [Direct Reply-To](https://www.rabbitmq.com/docs/4.1/direct-reply-to)). | `max_message_size` defaults to 16,777,216 bytes, enough for the current 10 MiB Cortex body ceiling plus a bounded envelope ([configuration](https://www.rabbitmq.com/docs/4.1/configure)). |
| **NATS JetStream + Core NATS** | JetStream stores the candidate and acknowledges publication; DG uses a durable consumer, then publishes the transient verdict to the sidecar's Core NATS reply subject. A plain Core `request()` would not persist the candidate ([JetStream publish/ack](https://docs.nats.io/learn/jetstream/publishing), [consumer acknowledgement](https://docs.nats.io/learn/jetstream/acknowledgment), [Core request/reply](https://docs.nats.io/learn/core-nats/request-reply)). | Server `max_payload` defaults to 1 MB; it can be raised, but NATS advises against values above 8 MB ([NATS 2.14 configuration](https://docs.nats.io/reference/2.14/config/max_payload)). |
| **Kafka 4.0** | Durable topics fit audit/replay, but a record key selects a partition rather than the specific sidecar holding the exchange. Per-sidecar topics/groups, manual partition ownership, or a router add scaling and churn work ([record key](https://kafka.apache.org/40/javadoc/org/apache/kafka/clients/producer/ProducerRecord.html), [consumer groups](https://kafka.apache.org/40/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html#consumergroups)). | Producer request default is 1,048,576 bytes and broker/topic batch defaults are 1,048,588 bytes; carrying a 10 MiB body needs coordinated tuning ([producer](https://kafka.apache.org/40/configuration/producer-configs/), [broker](https://kafka.apache.org/40/configuration/broker-configs/), [topic](https://kafka.apache.org/40/configuration/topic-level-configs/)). |

**Recommended first spike:** RabbitMQ quorum candidate queue plus Direct Reply-To if a complete body up to 10 MiB must fit one record. Its per-connection reply route and documented default size solve two concrete requirements that Kafka and NATS do not meet at their defaults. If the candidate body is capped near 1 MB, compare NATS JetStream plus a Core reply subject in the same spike. Kafka remains technically feasible, but its ordinary consumer-group pattern is not a per-sidecar reply route. RabbitMQ's own quorum-queue guidance warns about large-message workloads, so a 10 MiB candidate still needs throughput, disk, and latency measurements ([quorum queues](https://www.rabbitmq.com/docs/4.1/quorum-queues)).

The spike should measure candidate publication acknowledgement → DG consume → database commit → reply receipt at p99 and p99.9, including 1 MiB and 10 MiB bodies as applicable, representative proxy concurrency, pod churn, broker lag/restart, and DG restart. It must verify duplicate candidate handling and that lost/late replies cause the defined unavailable rejection within the configurable deadline. RabbitMQ Direct Reply-To and Core NATS inboxes do not acknowledge Cortex's application of the decision; with two application records, DG can audit its verdict but not an applied Block. Broker confirms, consumer acknowledgements, and replication add protocol traffic beyond the two application records.

## Coverage and semantics that the spike must expose

- **Visible traffic only.** The forward proxy gates decoded HTTP requests in `serveOutbound`; the current lineage plugin has parser dependencies but does not itself declare body access ([forward proxy](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/listener/forwardproxy/server.go#L284-L303), [body buffering](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/listener/forwardproxy/server.go#L357-L368), [lineage capabilities](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L196-L210)). `capture_io: false` means today's lineage spans carry no parsed request/response payload for DG classification ([attach configuration](../../deploy/lineage-attach/reconcile-existing-proxy.py#L99-L110)); a live decision's input must be specified separately.
- **Opaque CONNECT is not an inspected HTTP request.** AuthBridge gates CONNECT by destination before it opens a tunnel, but its inner bytes are unavailable to the ordinary HTTP parser path ([CONNECT hook](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/listener/forwardproxy/server.go#L1503-L1510), [pipeline invocation](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/listener/forwardproxy/server.go#L1574-L1586)). When TLS bridging succeeds, each decrypted request re-enters `serveOutbound`. But the CONNECT pipeline runs **before** bridge classification, and a bridge failure can fall back to opaque TCP after the tunnel's 200 response ([bridge selection and fallback](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/listener/forwardproxy/server.go#L1668-L1709)). A strict promise to reject every undecoded tunnel therefore needs listener changes; an `OnRequest` plugin alone cannot predict that later fallback.
- **Bypasses are distinct.** Listener `skip_hosts` bypasses the *entire* outbound pipeline, including any governance gate ([HTTP skip](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/listener/forwardproxy/server.go#L314-L353), [CONNECT skip](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/listener/forwardproxy/server.go#L1532-L1552)). Lineage's own `bypass_paths` and `bypass_hosts` currently skip span emission only ([lineage early returns](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L566-L587)). If enforcement is added to that same plugin, it must not accidentally inherit telemetry-only bypasses. Current Cortex also skips an agent's own local-service traffic before the pipeline when process attribution identifies it ([self-traffic skip](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/listener/forwardproxy/server.go#L333-L344)).
- **A Block is an attempted exchange, not delivered data.** If lineage emits its request span before the gate returns `Reject`, `OnFinish` can emit a `denied` outcome span ([lineage request](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L610-L643), [finish/outcome](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L825-L886)). DG derives an interaction for every outbound request span and collapses `denied`, `error`, and `abandoned` to an `error=true` response leg; the request leg has no outcome ([sidecar projection](../../data_governance/processors/interactions/sidecar.py#L234-L249), [outbound anchors](../../data_governance/processors/interactions/sidecar.py#L418-L485), [leg projection](../../data_governance/processors/interactions/sidecar.py#L536-L555)). Its lineage traversal accepts legs without an outcome/error field ([traversal leg shape](../../data_governance/processors/data_lineage/traversal.py#L111-L126)). The derived interaction alone does not prove upstream delivery or preserve the difference between a DG policy Block and a DG-unavailable rejection; the model should retain blocked attempts for audit while distinguishing them from data actually sent to the callee.
- **Telemetry is not a durable Block receipt.** Cortex's batch exporter is asynchronous and explicitly counts failed exports; a denied outcome span can be lost independently of the live decision ([batch exporter](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L451-L465), [export failure observer](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L530-L559)). If every Block must be durably auditable, DG should persist its decision before replying or provide a separately acknowledged audit path. That requirement is unresolved.

## Earlier option: same plugin or a separate gate

Both placements are feasible within the existing request hook. Extending `lineage-telemetry` would keep one configured plugin and let it emit the request span before asking DG, then emit the outcome in `OnFinish`. Its current description and package contract say it emits facts only, however, and its `not_ready`, `bypass_paths`, and `bypass_hosts` branches return `Continue`; enforcement would need its own scope and readiness behavior rather than inheriting those returns ([lineage contract and capabilities](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L1-L33), [early returns](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L566-L587), [request and finish hooks](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L610-L643)).

A separate governance gate could keep lineage telemetry's current role and run after it in the outbound pipeline. That order would let lineage emit a request span for a DG-blocked attempt before the gate rejects it; a gate placed before lineage would short-circuit the pipeline and produce no such spans ([pipeline short-circuit](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/pipeline/pipeline.go#L84-L130), [lineage ordering note](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L18-L29)). This also gives control and telemetry independent readiness and bypass configuration. Neither placement bypasses listener `skip_hosts` or solves opaque CONNECT fallback without the listener work above.

The current preference is to reuse the same plugin but replace its OTLP span export with the candidate/verdict queue path. That changes the plugin's facts-only contract and the two-span wire contract; it should be treated as a protocol migration, including DG ingestion and deployment wiring. Existing `not_ready` and telemetry-only bypass returns cannot be reused for an enforced request, while the trace-stamping work may still be needed to put selected-parent facts into the candidate ([plugin early returns and stamp](https://github.com/rossoctl/cortex/blob/93a3b74bec32941e68d9f61c98fd485e805141d9/core/plugins/lineage/plugin.go#L566-L625)).

## Verification target for the earlier DG-verdict spike

A stub DG decision service is enough to test the architecture before building a policy engine: concurrent, out-of-order Allow/Block replies must resolve only their matching held requests; a Block must leave the upstream hit count at zero; an Allow must forward exactly once; cancellation and disconnect must release pending state without forwarding; DG unavailability and the configured deadline must produce the chosen service-unavailable rejection (HTTP 503 for ordinary HTTP, or an MCP error frame for a parsed JSON-RPC request with an ID). For a queue, also test reply delivery to the correct proxy instance, duplicates/redelivery, late replies, broker lag, and rebalances against the deadline. A deployment check must prove that the chosen workload namespace can reach its control transport and verify the sender of verdicts. These tests would verify the control path, not DG policy quality.
